# Chrono.mbt Implementation Plan

Reference target: **chrono/time**-equivalent functionality (calendar arithmetic, `Duration`/`Span` types, IANA timezone database support), studied from two reference implementations:

- the Rust `chrono` crate
- the Go standard library `time` package

## Architecture Decisions (confirmed with the user)

- **Package layout**: start coarse, three packages under `src/`, split further only when a package's file count or independent test surface justifies it:
  - `src/core` — `Weekday`, `Month`, `IsoWeek`, `NaiveDate`, `NaiveTime`, `TimeDelta`, `NaiveDateTime`, the day-count/leap-year algorithm
  - `src/tz` — `Offset`/`TimeZone` abstraction, `Utc`, `FixedOffset`, the TZif parser, embedded tzdata asset, `Location` lookup
  - `src/format` — strftime-style formatting and parsing engine
- **Timezone strategy** (confirmed with the user after the Phase 6 spike): full IANA tzdata embedding, Go `time/tzdata`-style, via a standalone `scripts/gen_tzdata.py` that codegens `src/tz/tzdata_generated.mbt` as a `Bytes` array literal per zone (`([0xAA, 0xBB, ...] : Bytes)`), invoked manually (`just gen-tzdata <zoneinfo dir>`), not on every build. A feasibility spike first measured this scale (macOS `/var/db/timezone/zoneinfo`, 604 zones, ~840KB raw binary → ~5.2MB generated source) at ~1 second to `moon build`/`moon check --deny-warn` from a cold build on each of `native`/`wasm-gc`/`js` — no need for a more compact encoding (e.g. base64 + runtime decode). Implementation order: the TZif parser and `Location` type were implemented first against a handful of hand-picked real zones (as test fixtures); the codegen script embedding the full database came after, as a separate step within Phase 6.
  - **Correction found after this was first written**: MoonBit *does* have a native compile-time asset-embedding mechanism after all — `moon tool embed --binary` (invocable per-file from a package's `moon.pkg` via an `options."pre-build"` `":embed"` entry, as demonstrated by e.g. `connect0459/starlark-mbt`'s `src/internal/starlarktest/moon.pkg`). The original spike missed it by checking only `moon build --help`/`moonc --help`, not `moon tool --help`'s subcommands. Re-checked at the same 598-zone scale before deciding whether to switch: pre-build `:embed` outputs must live in the same package directory as the `moon.pkg` that declares them (no subdirectories), so using it here would mean restructuring the embedded zones into their own sub-package with 598 individual `.tzif` files plus a 598-entry generated `moon.pkg`, and it measured ~7x slower to build (~7s vs. ~1s) than the single-generated-file approach already implemented and tested. Kept the existing script-generated single file rather than switching, given it already works, is simpler structurally, and builds faster; a future switch to the native mechanism remains straightforward if those tradeoffs change.
- **Format/parse design**: strftime-style `%`-specifier engine (chrono-style), not Go's reference-time-layout style. Rationale: a `%`-token scanner is simpler to implement correctly than reference-layout matching (which must disambiguate numeric substrings like `1` as month vs. day by position in the reference string).
- **Cross-package `moon.pkg` imports**: declared only when a package's code actually references the dependency (`tz` importing `core` at the start of Phase 5, `format` importing `core`/`tz` at the start of Phase 7), not upfront when the package layout is created. Rationale: `moon check --deny-warn` (used by `just verify`) treats an unused import as an error, so declaring a dependency before any symbol from it is used would break CI immediately.
- **`TimeZone` trait gained a `tz_name` method** (confirmed with the user during Phase 7), so `format`'s `DateTime[Tz]` rendering can support `%Z` generically across every implementor: `Utc` → `"UTC"`, `FixedOffset` → its own offset string (`"+09:00"`, colon-separated, extended to `"+09:00:30"` for a non-whole-minute historical offset — mirrors chrono's `FixedOffset` `Display`), `Location` → the IANA abbreviation in effect at that instant (via the existing `type_at`). `%z` is rendered independently in `format` from the same offset, in strftime's plain `+HHMM` form (no colon, no sub-minute seconds) — distinct from `FixedOffset::tz_name`'s colon form, since `%z` and `%Z` are different specifiers with different conventional formats.
- **Calendar-step arguments stay plain `Int`; no `Months`/`Days` wrapper types** (confirmed with the user during Phase 11). chrono's `Months(u32)`/`Days(u64)` exist because Rust's unsigned counts cannot express direction and because `Add`/`Sub` are overloaded across `Months`, `Days` and `TimeDelta`. Here the signed `Int` already carries direction (a negative `months`/`days` runs the opposite way, so `add_*`/`sub_*` need no separate unsigned form), MoonBit has no operator/method overloading to dispatch on the wrapper, and the method names (`add_months`/`add_days`/`add_years`) already fix the unit. Wrapping would break the public `add_*`/`sub_*`/`checked_*` surface of `NaiveDate`/`NaiveDateTime`/`DateTime[Tz]` for no additional safety. Revisit only if a single entry point must accept several step kinds.
- **No zero-time predicate (Go's `Time.IsZero`) for `NaiveDateTime`/`DateTime[Tz]`** (confirmed with the user during Phase 11). Go's `IsZero` detects an uninitialized `Time`, which works only because Go's zero value is the year-1 epoch, a value real programs almost never hold. Here `Default` (and `unix_epoch()`) is the Unix epoch, a valid, commonly-held instant, so a predicate named for "zero" would misreport a real timestamp as unset. Equality against `NaiveDateTime::default()`/`unix_epoch()` already expresses "is the epoch", and an absent value is modeled by `Option[NaiveDateTime]`, not by a sentinel instant.
- **No binary marshalling (Go's `Time.MarshalBinary`/`UnmarshalBinary`) for the value types** (confirmed with the user during Phase 11). Go's binary form is the hook into `encoding/gob` and similar stdlib machinery, and MoonBit has no counterpart serialization trait for it to plug into. A published byte layout would also become a compatibility commitment, and the value types already round-trip through `Eq`/`Hash`/`Show` and the parsing entry points, so a caller needing a compact form can assemble one from the existing accessors (e.g. `timestamp()` plus `timestamp_subsec_nanos()`). This decision covers only the binary form; the `ToJson`/`FromJson` item in `src/format` is a separate design point and remains open.
- **No time-of-day combinators (`and_time`/`and_hms*`) on `MappedLocalTime`** (confirmed with the user during Phase 11). In chrono they are methods of `LocalResult<Date<Tz>>`, and `Date<Tz>` (a date bound to a zone) was deprecated in chrono 0.4.23. This project has no zoned-date type, and resolving a bare date to a zone is not meaningful: whether a local reading is a fold or a gap depends on its time of day. `MappedLocalTime` is therefore only produced for whole local date-times (`DateTime::from_local`, `from_ymd_hms`, `TimeZone::from_local_datetime`), which `NaiveDate::and_time`/`and_hms*` already feed into. Wrapping a date in a `MappedLocalTime[NaiveDate]` just to combine it later would be a value that is always `Single`, which the type would misrepresent.
- **No `DateTime::since`/`until` (Go's `Time.Since`/`Time.Until`)** (confirmed with the user during Phase 11). Reading the host clock inside a value method would make `DateTime`, otherwise a pure value type, nondeterministic and leave its tests able to assert only a range of durations. The clock is read in exactly one place, `Utc::now()`, and the same results compose from it: `Utc::now().signed_duration_since(dt)` for `since`, `dt.signed_duration_since(Utc::now())` for `until`. chrono offers neither.
- **No `NaiveDateTime`/`DateTime[Tz]` minimum and maximum constants (chrono's `MIN_UTC`/`MAX_UTC`, `NaiveDateTime::MIN`/`MAX`)** (confirmed with the user during Phase 11), for the same reason `NaiveDate::MIN`/`MAX` was rejected (see the `iter_days` item in Phase 10): the limit is a consequence of `Int` overflow analysis of the day-count algorithm, not a designed constant, and publishing it would freeze it against any later change of representation. A `DateTime[Tz]` bound would also need a zone argument. A caller probing the boundary gets `None` from the `checked_*` forms; this project's own tests share one private helper per package for the boundary day instead.
- **No `TimeZone::from_offset` (chrono's `TimeZone::from_offset(&Offset) -> Self`)** (confirmed with the user during Phase 11). A zone such as `Location` or `PosixTz` cannot be rebuilt from an offset alone, so a required trait method would force every implementor to fake it, and chrono's own `Utc::from_offset` silently discards the offset, a lossy conversion presented as a constructor. Nothing needs it here either: `DateTime::from_utc(naive, tz)` takes the zone value as an explicit argument, so generic code over `Tz : TimeZone` already holds one, and `with_timezone` re-expresses an instant in a concrete zone when a different one is wanted. A separate `FromOffset` trait for the zones that do keep the offset (`FixedOffset`, `FixedZone`) is left until a concrete use appears.
- **No `Z`-for-zero-offset specifier in the general formatter (Go's `Z07:00`)** (confirmed with the user during Phase 11). It would need a new specifier letter with no chrono counterpart and would overlap the `%z` family, while `%+`, `to_rfc3339` and `to_rfc3339_opts` (with its `use_z` choice) already render `Z` for a zero offset. Callers wanting RFC 3339's `Z` use those; the general `%z`/`%:z` family keeps rendering a numeric offset.
- **No arbitrary-width fractional-second specifiers (`%1f`..`%8f` and dotted forms) and no comma decimal separator** (confirmed with the user during Phase 11). `%3f`/`%6f`/`%9f` and `%.3f`/`%.6f`/`%.9f` cover the conventional millisecond, microsecond and nanosecond precisions, `%.f` covers a minimal width, and any other precision is a caller's truncation away. With `Item` now public, a digit count as a variant parameter would make invalid counts (`0`, `12`) representable and force a rule for them, while one variant per width would add twelve to `Numeric`; neither buys enough for a niche need. Go's comma separator (`,000`) would need a new specifier letter with no chrono counterpart; its parse-side half, a comma accepted after `%S`, is a strictness decision belonging to the open lenient-fractional-seconds item.
- **Whitespace in a format string stays an exact single-character match when parsing; no chrono-style `Item::Space`** (decided with the user during Phase 11). Strictness is the safer side of an asymmetry: accepting more input later is backward compatible, while tightening a tolerant parser later breaks inputs that used to parse. Tolerance also blurs boundaries (`%F %T` would accept `2024-03-0509:05:07`) and would widen the set the `*_default` parsers accept, which are meant to be exact inverses of `Show`; callers with messy input can normalize whitespace first or use the `_and_remainder` functions. `%n`/`%t` stay exact single characters too. If chrono-compatible tolerance is ever needed, it should arrive as an opt-in `Space` item (`Item` is public) rather than by changing what a space in a format string means.
- **`%S` does not implicitly read a following fractional second, and a comma is not accepted as the decimal separator** (decided with the user during Phase 11). `%S%.f` (or `%T%.f`) already reads a fraction when present and accepts its absence, so the lenient reading is one explicit specifier away. An implicit rule would break formats that are valid today, such as `%S.%3f`, unless it were switched off whenever a fraction item or a literal dot follows, leaving a special case in the specification that cannot be withdrawn once inputs depend on it; loosening later remains compatible. The comma half (Go's `,000`) was folded into this item earlier and is rejected on the same ground, and because it would also need a new specifier letter on the format side.
- **No `ToJson`/`FromJson` for the value types** (confirmed with the user during Phase 11). MoonBit's orphan rule lets an impl live only in the package that defines the type, so the impls would sit in `core` and `tz`, while the text layouts are parsed in `format`; a decoder would mean duplicating those parsers below `format` or moving them and inverting the layering, and an encoder without a decoder cannot serve a caller's `derive(ToJson, FromJson)`. The JSON shape itself (layout string versus numbers, which zone forms) is also the caller's policy, and publishing one would become a compatibility commitment. Callers already convert with `Json::string(x.to_string())` and the `parse_*_default` functions, which are exact inverses of `Show`. Adding the impls later is backward compatible, unlike removing them. This mirrors chrono, whose `serde` support is an optional feature rather than core.
- **No `rfc3339`, `rfc3339_nano` or `layout` named format constants** (confirmed with the user during Phase 11). Go's RFC 3339 layout means "`Z` for a zero offset, else `±hh:mm`", which no strftime string expresses (`%z` and `%:z` print the numeric zero offset), so a constant of that name would render differently from Go's and from `to_rfc3339`, which already exists beside `parse_rfc3339` and `%+`. Go's `Layout` is the reference time itself, a meta-constant that has no counterpart in a specifier-based design.
- **No lenient tokenizer (chrono's `StrftimeItems::new_lenient`)** (confirmed with the user during Phase 11). chrono's lenient mode exists so that formatting a user-supplied format string never panics; here `tokenize` and every `format_*`/`parse_*` already report a bad format by raising `ParseError`, so there is nothing to keep from failing. The consumers of an error item (rendering, parsing) would each gain an arm that only raises, with no use in this library, and adding a variant to the `pub(all)` `Item` enum breaks every external `match` on it. A caller who wants several diagnostics at once, as an editor would, is outside this library's scope.
- **No `write_format`-style variants that append to a caller's buffer (Go's `AppendFormat`)** (confirmed with the user during Phase 11). The only saving is the final `to_string` copy, since the cost of interpreting a format is tokenizing it, which `format_*_items` already lets a caller do once. Formatting can also raise partway (`MissingField`), so an appending API would leave half-written text in the caller's buffer, and restoring atomicity means rendering into a temporary buffer first, which removes the saving; Go's `AppendFormat` cannot fail, so its premise differs. Writing several values into one buffer is `builder.write_string(format_date(...))`. Adding the variants later is backward compatible.
- **No `OffsetFormat` (chrono's configurable `%z`-family struct)** (confirmed with the user during Phase 11). The practical renderings are already covered: `%z` (`±HHMM`), `%:z` (`±HH:MM`), `%::z` (`±HH:MM:SS`), `%:::z` (`±HH`), the permissive parse-only `%#z`, `FixedOffset`'s `Show` and `tz_name` (minutes, plus seconds only when nonzero), `to_rfc3339_opts`'s `use_z` (`Z` or `+00:00`), and `parse_fixed_offset` reading every form back. `allow_zulu` is in effect `use_z`. A public options struct would make its field combinations a compatibility commitment, duplicate what the specifier syntax already states, and sit awkwardly beside the decision not to add a `Z` rendering to the general formatter. Adding it later is backward compatible.
- **Failure reporting is split by failure kind, not unified under one syntax** (confirmed with the user during Phase 12). The four mechanisms answer different questions: `Option` says "no such value" (constructors, `checked_*`), abort says "the caller broke a documented precondition" (plain arithmetic, `digits` outside `0..=9`, `MappedLocalTime::unwrap`), `Result[T, RoundingError]` says "this argument or result is rejected" for pure value computation (`round`/`round_up`/`truncate`/`round_subsecs`), and `raise ParseError` says "this input text is malformed" in `format`. `RoundingError` stays a plain `Result` payload rather than a `suberror`: the rounding functions are pure value transformations that callers compose with `map`/`bind`, and `raise` would force a `try` at every call site and block that composition, while the parse functions already sit at a text boundary where raising is the norm. Changing one to the other later is breaking in both directions, so the split is recorded here.
- **`NaiveTime::round_subsecs` wraps past midnight and discards the day carry** (confirmed with the user during Phase 12). A time of day has no calendar to carry into, so wrapping is intrinsic, matching `wrapping_add_signed`. A caller that needs the carry uses `NaiveDateTime::round_subsecs`, which moves the date forward (or fails with `OutOfRange` at the top of the range). `NaiveTime` keeps only the `digits`-based `round_subsecs`/`truncate_subsecs` and no `TimeDelta`-granularity `round`/`truncate`.
- **`DateTime[Tz]` is identified by its UTC instant for `Eq`, `Hash` and `Compare`** (confirmed with the user during Phase 12). Deriving `Eq`/`Hash` over `(instant, zone)` while `Compare` used the instant alone let two values compare `0` yet be unequal, which breaks the contract that ordering and equality agree and makes sorting or deduplicating a mixed-zone collection ambiguous. A single notion of identity, the instant, matches chrono and means `Tz` needs no `Eq`/`Hash`, so a zone type's own equality (`Location` compares its `name`) no longer decides whether two instants are equal. The zone remains observable through `offset()`, `zone()`, `zone_name()` and `naive_local()`, and `Show`/`Debug` still print it; a caller who needs "same instant and same zone" compares the zone explicitly.
- **`Absent` also reports components that form no valid local reading** (confirmed with the user during Phase 12). `DateTime::from_ymd_hms`, `DateTime::with_*` and `format::parse_date_time_in` return `Absent` both for an invalid component (month 13) and for a reading inside a DST gap. Both mean "no local instant corresponds to this input", and a caller acts the same way on either (nothing to use), so the merge loses no decision a caller can make; one who must distinguish validates with `NaiveDate::from_ymd`/`NaiveTime::from_hms` first. Wrapping the result as `MappedLocalTime[T]?` would separate them but force a two-level match at every call site and break composition with `single`/`earliest`/`latest`. The rule is stated on `MappedLocalTime` and in the README.
- **`format` suffixes name where the zone comes from; `_default` means the inverse of `Show`** (confirmed with the user during Phase 12). `_tz` renders any `DateTime[Tz]` (`format_date_time_tz`), `_in` reads the local clock in a caller-supplied `Tz` (`parse_date_time_in`), and `_fixed_offset` reads the offset written in the input (`parse_date_time_fixed_offset`, after its `DateTime[FixedOffset]` result and `DateTime::fixed_offset`). The RFC functions follow `<verb>_rfcNNNN` (`to_rfc2822`, `parse_rfc2822`, `to_rfc3339`, `parse_rfc3339`), which departs from chrono's `parse_from_*` for consistency inside this library. `parse_date_time_utc_default` has no fmt-taking `parse_date_time_utc` counterpart on purpose: `_default` is the exact inverse of a type's `Show`, a role a format-string parser does not have, and `parse_date_time_in(input, fmt, Utc::new())` already reads UTC with any format. Adding `parse_date_time_utc` later is backward compatible.
- **`TimeZone` stays a readonly trait; the zone set is closed** (decided with the user during Phase 12). `pub trait TimeZone` is readonly in MoonBit, so a package outside `tz` can bound on it but cannot implement it (the compiler rejects it with "Cannot implement trait ... because it is readonly"); the zones are `Utc`, `FixedOffset`, `FixedZone`, `Location`, `PosixTz` and, on native, `Local`. Closing it keeps every later change to the trait compatible, including a new required method, and leaves `from_utc_datetime`/`from_local_datetime` free of any override contract. Opening it (`pub(open)`) is backward compatible, so it waits for a concrete need for a caller-defined zone, at which point the UTC-versus-local `NaiveDateTime` ambiguity and the two spellings of `from_utc`/`from_local` should be settled first, because an open trait would freeze them.
- **`DateTime::from_utc`/`from_local` are the only spelling; `TimeZone` names which `NaiveDateTime` reading it takes** (decided with the user during Phase 12). `TimeZone::from_utc_datetime`/`from_local_datetime` were removed: their defaults only delegated to `DateTime::from_*`, nothing outside the package could override them, and Phase 11 had already declined `and_utc`/`and_local_timezone` as further spellings. Every `NaiveDateTime` argument of a `TimeZone` method is a UTC reading except `offset_from_local`'s, which is a local reading, and the trait docstring and README now say so. Separate `UtcDateTime`/`LocalDateTime` types were rejected: they would change every API that takes a `NaiveDateTime`, while the misuse is confined to callers invoking the trait directly (the `DateTime` accessors pass the right reading), and the method names `offset_from_utc`/`offset_from_local` already state the reading where it matters most. Renaming the UTC-reading methods was rejected too, since it would diverge from the `%Z` and `zone_name` vocabulary.
- **`PosixTz` queries take a UTC `NaiveDateTime`; `offset` means `FixedOffset`, `utc_offset` means seconds** (decided with the user during Phase 12). `PosixTz::type_at` now takes the same UTC reading as `Location::type_at` and every `TimeZone` method, and its validity window is reached through `TimeZone::transition_bounds` (returning `TransitionBounds`) instead of a raw `(Int64, Int64)` tuple; the Unix-seconds forms stay private for `Location`'s own lookups. `PosixTz::offset_at` and `bounds_at` were removed: `type_at(..).utc_offset()` and `transition_bounds` cover them, and `offset_at` returned an `Int` under a name that means `FixedOffset` elsewhere. The rule is stated in the README: `offset`/`offset_from_*` yield a `FixedOffset`, `utc_offset`/`local_minus_utc` yield seconds as an `Int`.
- **The `format` enums stay `pub(all)` and grow as a breaking-change class; `Item` equality is syntactic** (decided with the user during Phase 12). `Item`, `Numeric`, `Fixed`, `PadMode` and `SecondsFormat` are inputs that callers build by hand for `parse_items` and the `format_*_items` functions, so a readonly `pub` enum (matchable but not constructible) would remove that ability, and it would not protect an external exhaustive `match` from a later variant anyway. New specifiers therefore add variants and are released as breaking changes, which the README states. `Item` equality compares the specifier as written, so `%H` (`Numeric(Hour)`) and `%0H` (`PaddedNumeric(Hour, ZeroPad)`) render alike yet differ; that keeps the caller's flag visible to `tokenize` round trips and diagnostics, and the docstring says so. The fractional-second variants are spelled by digit count (`Nanosecond3`/`6`/`9`, `DotNanosecond3`/`6`/`9`) and the two-digit year forms by `Mod100` (`YearMod100`, `IsoYearMod100`).
- **A `LocalTimeType` offset is always a valid `FixedOffset`** (decided with the user during Phase 12). `LocalTimeType::new` returns `Option` and rejects an offset beyond `±86399` seconds, and `parse_tzif` and `parse_posix_tz` return `None` for one. Validating only `new` would not have been enough: both parsers built such values directly (`parse_posix_tz("XXX-99")` succeeded), and the `TimeZone` lookups of `Location` and `PosixTz` convert every offset with `FixedOffset::east(..).unwrap()`, so a crafted rule string or TZif buffer could abort the process. With the invariant established at the three places an offset enters, those `unwrap`s are sound. A whitebox test loads every embedded zone to guard the parser change.
- **`parse_tzif` validates the structure it will later index** (decided during Phase 12, as a follow-up to the offset invariant). A crafted buffer could abort a lookup or read past the data: a transition naming a local time type that does not exist, no local time type at all, an abbreviation index past or unterminated inside the designation block, and negative header counts or counts whose section sizes overflowed `Int` and passed the length check. All now return `None`. Transitions that are not strictly increasing, which RFC 8536 forbids and which would silently break the binary search, are rejected too. The embedded database still loads in full (covered by the whitebox test added with the offset invariant).
- **`Location` and `PosixTz` queries are total over the representable date range** (decided during Phase 12). Driving `Location` with crafted 64-bit TZif data and with real zones at the ends of `NaiveDate`'s range found two aborts that the TZif structural validation does not cover. `Location::transition_bounds` converted each transition to a `NaiveDateTime` with `unwrap`, so a transition outside the range (legal in a 64-bit TZif) aborted; such a side is now reported as unbounded. POSIX rule evaluation built each year's rule dates with `unwrap` and unchecked `add_days`, so any zone with a POSIX footer, including `America/New_York`, aborted for instants in the last representable years; a year whose rule dates fall outside the range now counts as standard time, and a neighbouring year outside it leaves that side of a window unbounded. The cases are kept in `location_extremes_test.mbt`. `DateTime` itself still aborts where its own arithmetic leaves the range (for example `naive_local` of the last representable instant at a positive offset); that is the documented abort contract, not part of this decision.
- **Only intended helpers are public: the civil-date and tzdata-lookup helpers are private, `is_leap_year` stays** (decided with the user during Phase 12). `core::days_from_civil`/`civil_from_days` are unchecked conversions (an invalid month or day still yields a value) used only inside `core`, and `tz::resolve_tzdata_bytes` is called only by `Location::load`; `NaiveDate::from_ymd`/`epoch_days`/`from_epoch_days` and `Location::load` cover what a caller needs, with validation, so their tests moved to whitebox tests and they left the READMEs. `core::is_leap_year(Int)` stays as a documented API: a predicate over a bare year has no input restriction, callers without a `NaiveDate` need it, and `tz` uses it.
- **`Utc` stays a readonly struct, and `Location` equality includes its name** (decided with the user during Phase 12). `pub struct Utc {}` is already readonly in MoonBit: code outside `tz` cannot write `Utc::{}` (the compiler rejects it), so `Utc::new()` is the only way to obtain the value and stays as that constructor; nothing needed changing. `Location` equality and hashing stay structural over the parsed TZif data, the POSIX rule and `name()`, so a zone reached through an alias (`Japan`), or built without a name, differs from the canonical one (`Asia/Tokyo`) even when both resolve identically; `Location` is a named zone, its `Show` and `name()` agree with its identity, and equality ignoring the name would let equal values print differently and collapse aliases as `Map` keys. Since `DateTime` equality is by instant (see that decision), this only affects comparing or keying `Location` values themselves.
- **A named constructor is the canonical spelling of a default value, and `default()` delegates to it** (decided with the user during Phase 12). `TimeDelta::zero`, `NaiveTime::midnight`, `WeekdaySet::empty`, `NaiveDateTime::unix_epoch` and `DateTime::unix_epoch` stay beside `Default`, as in chrono, which pairs `derive(Default)` with `TimeDelta::zero`, `NaiveTime::MIN`, `WeekdaySet::EMPTY` and `DateTime::UNIX_EPOCH`; Go offers no named form and relies on its language zero value, which this library does not share. A call site reads `TimeDelta::zero()` where `TimeDelta::default()` would not say what the value is, while `Default` stays available to generic code. The two cannot drift apart because each `default()` is defined as a call to its named constructor, and each docstring says so. `NaiveDate` has a `Default` (the epoch) but no `unix_epoch`, since its value is a date rather than an instant and `NaiveDate::from_ymd(1970, 1, 1)` already names it.
- **`TimeDelta::max_value`/`min_value` are a designed, frozen contract; date types publish no extremes** (decided with the user during Phase 12). The rule is whether the range is a designed property of the type or a by-product of its representation. `TimeDelta`'s bound of `±9_223_372_036_854_774` seconds is chosen so that `num_milliseconds` always fits in `Int64` and so that the range is symmetric, which makes `neg` and `abs` total; callers can rely on both, and chrono publishes `TimeDelta::MIN`/`MAX` too. The date types' limits, by contrast, fall out of `Int` overflow analysis of the day-count algorithm and stay unpublished (Phase 11). The exact `TimeDelta` values are therefore frozen, the docstrings say so, and widening the range later would need its own decision.
- **Integer widths: fixed-length counts are `Int64`; calendar steps, fields and scalars are `Int`** (decided with the user during Phase 12). A count of fixed-length time (seconds, milliseconds, microseconds, nanoseconds, timestamps, and the `TimeDelta` unit constructors), or a difference that can exceed `Int` (`NaiveDate::abs_diff`, `TimeDelta::num_*`), is `Int64`, because `NaiveDate` spans millions of years and a span in seconds leaves `Int`. A calendar step (`add_days`, `add_months`, `add_years`, whose result must land in range, so `Int` reaches all of it), a calendar or clock field, the sub-second component of `from_timestamp` (always within one second) and a scalar multiplier or divisor (`TimeDelta::mul`/`div`, as chrono's `i32`) are `Int`. The one exception was `NaiveDateTime::add_seconds` and its `sub_`/`checked_` forms, limited to about 68 years; they now take `Int64`.
- **`Compare` only where one natural total order exists** (decided with the user during Phase 12). A type implements `Compare` when every user agrees on its order: chronological for `NaiveTime`, `NaiveDate`, `NaiveDateTime`, `IsoWeek`, `NaiveWeek` (by its first day) and `DateTime` (by instant, as `Eq` is); magnitude for `TimeDelta`; calendar-year order for `Month`. `Weekday` has none because its order depends on the locale's first day, `WeekdaySet` had one only by bit layout, which says nothing about the sets and disagrees with `is_subset`, so it was removed (`is_subset` is the meaningful relation). `FixedOffset`, `FixedZone`, `Utc` and `Location` have none: "greater offset means further east" is a convention rather than a shared order, `local_minus_utc()` compares offsets when wanted, and adding `Compare` later would be backward compatible.
- **Trait coverage: `Eq` and `Debug` on every public value type, `Show` only with a canonical text form and its parser** (decided with the user during Phase 12). `Eq` and `Debug` (a structural dump, which `assert_eq` needs to report a failure) are provided for all public value types; `Parsed`, `Location` and `TzifData` gained what they lacked. `Show` stays reserved for types that have a canonical text form and a parser that reads it back (`parse_*_default`, `parse_duration`, `parse_fixed_offset`), which keeps the claim behind declining `ToJson`/`FromJson`, that `Show` and those parsers are exact inverses, true. `NaiveWeek`, `LocalTimeType`, `PosixTz`, `TransitionBounds`, `MappedLocalTime`, `TzifData` and `Parsed` have no canonical text and no parser, so they get no `Show`, since one would be a format to keep compatible and would blur that property. The `Debug` of a `Location` or `TzifData` expands the whole transition table and is long for a real zone.
- **Three packages stay, with a thin root facade** (decided with the user during Phase 12). The split into `core`, `tz` and `format`, their names and the placement of `DateTime` in `tz` are final, since moving a type or renaming a package is breaking after release. The root package `connect0459/chrono`, which exported nothing, now re-exports with `pub using` the everyday types only: `Weekday`, `Month`, `NaiveDate`, `NaiveTime`, `NaiveDateTime`, `TimeDelta`, `TimeZone`, `Utc`, `FixedOffset`, `Location`, `DateTime` and `MappedLocalTime`. The aliases are the original types, so values interchange with those of `core` and `tz`; functions are not re-exported, so `format` stays a separate import. This follows the sibling `starlark-mbt`, whose root package re-exports a few types and adds entry points. `format` remains free functions because a method on a type owned by another package cannot be declared there, so `dt.to_rfc3339()` does not exist while `DateTime::to_string` does. The `@core` alias default can be confused with the standard library's `moonbitlang/core`; the package names are kept and the root README shows how to import with another alias.
- **Iterators are consumed positions; the values they walk stay immutable** (decided with the user during Phase 12). `NaiveDateDaysIterator`, `NaiveDateWeeksIterator` and `WeekdaySetIterator` mutate themselves in `next`/`next_back`, the one place the library is stateful, which matches MoonBit's own `Iter` (a closure over state). The values they walk (`NaiveDate`, `WeekdaySet`) are never changed, and each of `iter_days`, `iter_weeks` and `iter_from` returns a fresh iterator. `iter()` does not advance an iterator but returns an `Iter` sharing its state, so consuming that `Iter` consumes the original. A pure alternative (returning the item with a new iterator) would not work with `for` loops or the `Iter` adapters. The behaviour is stated in each type's docstring and the README, and tested.
- **`DateTime::date` replaces `date_naive`; `Month::num_days` and `NaiveDate::num_days_in_month` stay** (decided with the user during Phase 12). chrono names the zoned accessor `date_naive` because its `DateTime::date()` returned the deprecated zone-carrying `Date<Tz>`. This library has no such type (Phase 11), so nothing collides, and `date_naive` beside `time()` (which also returns a naive value) was uneven, so it is now `DateTime::date()`, matching `NaiveDateTime::date()`. `Month::num_days(year)` and `NaiveDate::num_days_in_month()` keep chrono's names: a month alone needs the year as an argument while a date already has one, each reads naturally on its receiver, and the docstrings point to each other.

## Phase 8: Rounding & Truncation

Reference: chrono's `Round`/`SubsecRound` traits, Go's `Time.Round`/`Time.Truncate`/`Duration.Round`/`Duration.Truncate`.

Coverage target (confirmed with the user): 100%.

Design decisions (confirmed with the user before implementation):

- **Reference point**: the Unix epoch (`1970-01-01T00:00:00`), not Go's year-1 zero time — consistent with this codebase's existing `timestamp()` family, unlike Go's `Time` internal representation. `NaiveDateTime::round`/`truncate` compute the `TimeDelta` since the epoch via the already-total `signed_duration_since`/`add_signed`, rather than converting through `timestamp_nanos()` (which is `Option`-returning and can overflow for a date far from the epoch) — this keeps the date side of rounding/truncation free of spurious overflow.
- **`granularity` is restricted to two shapes**: purely sub-second (a whole number of nanoseconds, no whole-second component) or a whole-second-or-larger multiple (no sub-second remainder). A "mixed" granularity (e.g. 1.5 seconds) returns `None`. Rationale: `TimeDelta`'s `seconds` component is far too large to convert to a single nanosecond count in the general case (mirrors why `num_nanoseconds` is already `Option`-returning), and supporting arbitrary mixed granularities in general would require arbitrary-precision arithmetic (Go's own `Duration`-vs-`Time` general case falls back to manual 128-bit arithmetic for exactly this reason). Every named duration unit (ns/µs/ms/s/min/hour/day/week/...) falls into one of the two supported shapes, so this is not a practical limitation.
- **Invalid `granularity` (zero or negative) is rejected** (originally `None`, now `Err(InvalidGranularity)` — see the typed rounding failure item in Phase 11), not Go's silent no-op passthrough — consistent with this codebase's existing `TimeDelta::div` convention of rejecting invalid input via `Option` rather than a silent identity result.
- **Half-value ties round away from zero** (matches Go's `Duration.Round`); **truncation always rounds toward zero/the epoch**, never toward negative infinity — verified explicitly for a pre-epoch `NaiveDateTime`, where truncating moves the datetime *forward* in time.
- **`DateTime[Tz]::round`/`truncate` operate on the underlying UTC instant**, not the offset-shifted local presentation (matches Go's and chrono's documented behavior): truncating to an hour boundary in UTC may still report a non-zero local minute under a non-whole-hour `FixedOffset`.

- [x] Round/truncate a `NaiveDateTime`/`DateTime` to an arbitrary `TimeDelta` granularity since the epoch (prefer Go's general single-`div`-helper approach over chrono's two-trait split — simpler, and not limited to decimal subsecond digits)
- [x] Round/truncate a `TimeDelta` itself to a multiple of another `TimeDelta`
- [x] Tests: half-value rounds away from zero; truncation always rounds toward the epoch; round/truncate by a duration larger than the value itself

## Phase 10: API Surface Gap Follow-ups

Reference: a feature-level gap survey against the Rust `chrono` crate and Go's `time` package (see `CLAUDE.local.md` for where the reference implementations are kept locally), covering all three packages (`src/core`, `src/tz`, `src/format`).

Two items originally required a design decision before any implementation work started, since they touch this library's core design premise that every operation is a pure function of caller-supplied instants, with no hidden wall-clock or OS access. Both are now resolved (confirmed with the user):

- [x] **Design decision (resolved)**: `Utc::now()` is added. The original premise ("`native` has OS clock access; `js`/`wasm-gc` do not") was checked against `moonbitlang/core`'s actual sources (`~/.moon/lib/core/env`) and found to be wrong: `@env.now()` (ms since the Unix epoch) is implemented symmetrically across all four backends (`native` via C FFI, `js` via `Date.now()`, `wasm`/`wasm-gc` via the `__moonbit_time_unstable` host import). `Utc::now() -> DateTime[Utc]` is implemented in its own file (`src/tz/now.mbt`), isolated from the package's otherwise-pure functions, wrapping `@env.now()`.
- [x] **Design decision (resolved)**: `Local` is added, scoped to `native` only. Unlike `now()`, a real asymmetry does exist here: `$TZ` is readable symmetrically via `@env.get_env_var`, but reading the `/etc/localtime` fallback (the common case when `$TZ` is unset) requires file I/O, which `moonbitlang/core` does not provide on any backend — `native` can add its own C stub (`native-stub` in `moon.pkg`, confirmed as a real MoonBit mechanism), but `js`/`wasm-gc` cannot without a host-provided file-read import that doesn't exist. `Local` is therefore compiled only for `native` (via `moon.pkg`'s per-file `targets`, the same mechanism `moonbitlang/core/bench`'s `monotonic_clock_*.mbt` uses), not present at all on other backends. Scoped to `$TZ` as an IANA zone name (via `Location::load`) falling back to `/etc/localtime` bytes (via `Location::from_tzif_bytes`); a bare POSIX rule string in `$TZ` (e.g. `EST5EDT`) is out of scope for this item — see the `PosixTz`-as-`TimeZone` item below, which would need to land first. **Superseded in Phase 11**: `Local::resolve` now accepts a bare POSIX rule; see the `PosixTz` item in Phase 11's `src/tz` section.

Coverage target: 100%, consistent with Phase 1–8 (confirmed with the user), except for the thin OS-facing shim functions (`Utc::now()`, `Local::new()`) which read live host state and are covered only by a sanity check, not exhaustive branch coverage — the resolution logic itself is factored into pure, fully-covered functions tested with fixture data (`Local::resolve`).

### `src/format`

- [x] Specifiers wired to already-existing `core`/`tz` primitives (low cost): `%b`/`%B`/`%h` (month name, via `Month::name()`), `%I`/`%l`/`%P`/`%p` (12-hour clock, via `NaiveTime::hour12()`), `%s` (Unix timestamp, via `timestamp()`), `%G`/`%g`/`%V` (ISO week-date, via `IsoWeek`). - [x] Remaining year/day/weekday/week-number specifiers: `%C`, `%y`, `%q`, `%e`, `%w`, `%u`, `%U`, `%W`. All eight got full format **and** parse support (confirmed with the user, choosing chrono-equivalent completeness over deferring the harder half, unlike the previous specifiers item's `%s`/`%G`/`%g`/`%V` format-only split): `%q` cross-checks against an already-determined date, like `%A`/`%a`, since a quarter alone can't determine a day; `%e` merges into `%d`'s field and `%w`/`%u` into `%A`/`%a`'s `weekday` field, since each pair represents the identical value in a different rendering; `%C`/`%y` reconstruct a year via a new `resolve_year` that mirrors chrono's own reconciliation (`%C`+`%y` combine directly, `%y` alone applies the conventional two-digit-year pivot — `< 70` -> 20xx, `>= 70` -> 19xx — and a negative `%Y` combined with either is rejected outright, since a negative year has no well-defined century/modulo split); `%U`/`%W` (US-style, Gregorian-year week numbers, distinct from `%V`'s ISO week-date numbering) combine with a weekday to construct a date via a new `resolve_date_from_week`/`week_based_yday`, mirroring chrono's own support for week-date parsing, when no month/day/ordinal is given, and otherwise cross-check against the constructed date; `week_number` (the formula shared by `%U`/`%W`'s formatting and `resolve_date_from_week`'s inverse) was derived and verified against real `strftime` output across several known edge-case years rather than ported from a reference implementation. No new `core` primitives were needed (`Weekday::num_days_from_sunday`/`num_days_from_monday`/`number_from_monday` and `NaiveDate::quarter` already existed). This unblocks a future revisit of `%G`/`%g`/`%V` parsing (ISO week-date construction, distinct machinery from `%U`/`%W`'s Gregorian-year construction added here) — not done in this item, since it wasn't part of its listed scope.
- [x] Compound specifiers: `%D`, `%x`, `%v`, `%R`, `%X`, `%r`, `%c`, `%+`. Seven of the eight (`%D`, `%x`, `%v`, `%R`, `%X`, `%r`, `%c`) are pure tokenizer expansions into already-existing `Item`s (identical in kind to the existing `%F`/`%T` expansion), so format **and** parse support came for free from already-tested machinery — no new render/parse logic, matching chrono's own default (non-locale) `D_FMT`/`D_T_FMT`/`T_FMT`/`T_FMT_AMPM` definitions (this project has no locale support, so `%x`/`%X`/`%c` are simply identical to `%D`/`%T`/its own ctime-style expansion, rather than switching on a locale). `%R` (hour:minute only) cannot alone satisfy `parse_time`, which requires a seconds field — an existing, unrelated constraint of `resolve_time`, not a new limitation introduced here. `%+`, confirmed with the user, got full support by extending a new top-level `Item::Rfc3339` variant (not nested under `Numeric`/`Fixed`, since it represents a whole date-time, not a single field) that delegates to the existing Phase 7 RFC 3339 fast path: `to_rfc3339`/`try_parse_rfc3339` were refactored to extract reusable `render_rfc3339`/`parse_rfc3339_datetime` helpers (behavior-preserving; `parse_rfc3339_datetime` drops the original's end-of-input requirement so it composes inside the general token walker), and `%+`'s parsed fields merge into the same `Parsed` accumulator via the existing `merge_field` mechanism, so `%+` cross-checks naturally against any other specifier in the same format string.
- [x] Variable-width/dot-prefixed fractional seconds: `%.f`, `%3f`, `%6f`, `%9f` (only the fixed 9-digit `%f` exists today). Two design points confirmed with the user: `%.f`'s rounding reuses the existing `format_fraction_trimmed` helper (full minimal-significant-digit trim, e.g. `120ms -> ".12"`) rather than chrono's own `%.f` behavior (snaps to whichever of 3/6/9 digits divides evenly, e.g. `120ms -> ".120"`) — chosen for internal consistency with this project's own already-confirmed RFC 3339 fraction convention (`%+`) over literal chrono parity; and `%.f` is genuinely optional on parse (mirrors chrono: absent input, i.e. no leading dot, leaves the nanosecond field untouched and does not raise) — the first specifier in this project to have that property, self-contained in its own `apply_item` arm (`parse_rfc3339_fraction`, reused directly — it already returns `Some((0, pos))` for "no dot present"), no change needed to `parse_items`'s general walking loop. `%3f`/`%6f` are new `Numeric` variants (fixed-width, no dot, mandatory, truncating — not rounding); `%9f` reuses the existing `Numeric(Nanosecond)` item directly (identical rendering/parsing to bare `%f`) rather than adding a redundant variant. `tokenize` gained its first multi-character lookahead (`%.f`/`%3f`/`%6f`/`%9f` are 3 characters after `%`, advancing `i + 3` instead of the uniform `i + 2` every other specifier uses) — a structural first for the tokenizer, though contained entirely within the new match arms. `%.3f`/`%.6f`/`%.9f` (dot **and** fixed-width) were not implemented, since they are not part of this item's listed scope. **Superseded in Phase 11**: `%.f`'s minimal-digit trimming (the divergence from chrono described here) was replaced by chrono's 3/6/9-digit rendering; see the fractional-seconds consistency item in Phase 11's `src/format` section.
- [x] TZ colon-offset variants: `%:z`, `%::z`, `%:::z`, `%#z` (only bare `%z` exists today). A counterintuitive finding from chrono's actual source, confirmed against it directly: more colons means **less** precision, not more — `%:z` is `±HH:MM`, `%::z` is `±HH:MM:SS` (always with seconds), `%:::z` is `±HH` (hours only, minutes/seconds dropped entirely). Two design points confirmed with the user: (1) `%:z`/`%::z`/`%:::z` parse **strictly**, matching only their own rendered shape (colon mandatory, exact field widths) — diverging from chrono's own parser, which shares one lenient implementation across all four `%z` variants (colon optional, minutes mandatory but seconds silently ignored even for `%::z`) — chosen for consistency with this project's already-established "`%z` parses exactly its render width" philosophy over literal chrono parity; (2) `%#z`, confirmed as parse-only (mirrors chrono, which panics if used to format — this project raises `MissingField` instead), got chrono's full permissive grammar: `Z`/`z` for zero, else a sign (`+`/`-`/U+2212 MINUS SIGN, all three, matching chrono) plus mandatory 2-digit hours, then any run of `:`/space/tab (or none) before an *optional* 2-digit minutes (default `0`) — no seconds field at all, since chrono's own shared parsing engine doesn't read one either for any `%z` variant (confirmed by reading chrono's `scan::timezone_offset`, which blindly discards up to two trailing characters after minutes without validating or incorporating them as seconds — an apparent implementation quirk, not a documented feature, and deliberately *not* reproduced here). `tokenize` gained its second and third instances of multi-character lookahead in this phase (after `%.f`/`%N f`): counting a run of 1–3 colons before `z`, and a `#` immediately before `z`.
- [x] Padding-flag modifiers: `%-?`/`%_?`/`%0?`. Scope confirmed with the user: applies generally, to every eligible `Numeric` specifier, rather than an arbitrarily-chosen subset — required refactoring `tokenize`'s previously-monolithic per-character match into a reusable `resolve_specifier` (returning `(Array[Item], Int)`), called both from the normal path and the new flag path (which resolves *what follows the flag* the same way, to check it's a single bare `Numeric` item before wrapping it — mirrors chrono, which only allows a flag on its own single `Numeric`-carrying item, rejecting it on a `Fixed` item or a multi-item compound expansion like `%F`). A key finding from chrono's actual source, confirmed by reading it directly: padding flags are **format-only** — chrono's own parser destructures `Item::Numeric(spec, _pad)` with `_pad` explicitly unused, so parsing a flagged specifier behaves exactly like the bare one. This meant the new `Item::PaddedNumeric(Numeric, PadMode)`'s parse-side needed no new logic at all: it just delegates via `apply_item(Numeric(kind), parsed, chars, pos)`, reusing the unwrapped specifier's existing, already-tested parsing verbatim. The fractional-second family (`%f`/`%.f`/`%3f`/`%6f`) and `%s` are `Numeric` in this project (for implementation convenience) but map to `Fixed` in chrono (so chrono itself rejects a flag on them) or have no natural fixed width (`%s`); `tokenize` excludes exactly these from `PaddedNumeric` eligibility to match chrono's real behavior despite this project's different internal classification. Rendering needed a new `numeric_value` helper (raw value + default width per `Numeric` kind, for the 19 eligible kinds) that `PaddedNumeric` calls before applying the override padding — its match is necessarily exhaustive over the full `Numeric` enum (a MoonBit requirement), so it also carries a `Nanosecond | DotFraction | Nanosecond3 | Nanosecond6 | Timestamp => raise MissingField(item)` arm that's genuinely unreachable by construction (`tokenize` never produces `PaddedNumeric` with one of those kinds) — confirmed via `moon coverage analyze`, which flags exactly that one arm and nothing else, documented here rather than forced into artificial test coverage (CLAUDE.md: don't add validation for scenarios that can't happen). The existing bare-`Numeric` render/parse arms were deliberately left untouched (not refactored to share `numeric_value`) to avoid regression risk in already-shipped, already-tested code for a supposedly-additive feature.
- [x] RFC 2822 fast path: `to_rfc2822`/`parse_from_rfc2822`, mirroring the existing RFC 3339 fast path. Design confirmed with the user: `parse_from_rfc2822` is **strict**, accepting only the exact shape `to_rfc2822` itself renders — not chrono's real parser, which additionally supports RFC 2822's "obsolete format" (optional day-of-week, arbitrary/folding whitespace, 2-/3-digit year windowing via a century-guessing heuristic, named legacy zones like `GMT`/`EST`, single-letter military zones as `-0000`, and parenthesized comments). This mirrors the same strictness already chosen for this project's RFC 3339 fast path. `to_rfc2822` reuses existing helpers verbatim (`weekday_short_name`, `month_short_name`, `pad_int`, `format_offset_no_colon`) and renders the day **unpadded** (`date.day().to_string()`, one or two digits, never a leading zero) — confirmed directly from chrono's own `write_rfc2822` source, which writes a single raw digit char for day < 10 rather than zero-padding, contradicting its own doc comment's claim of being "same as `%a, %d %b %Y %H:%M:%S %z`" (`%d` zero-pads elsewhere in this project). Unlike `to_rfc3339` (total), `to_rfc2822` raises a new `InvalidRfc2822` `ParseError` variant when the year falls outside RFC 2822's own `0..=9999` range — chrono itself enforces the same restriction (panicking rather than raising, since chrono's `to_rfc2822` isn't fallible by signature). `parse_from_rfc2822` is written as a flat sequence of steps via a small generic `rfc2822_require[T](T?) -> T raise ParseError` helper (raising `InvalidRfc2822` on `None`) rather than the deeply-nested `match` chain a positional-Option-threading style would otherwise produce for RFC 2822's much longer field sequence (weekday, day, month, year, hour, minute, second, offset) — a cleaner style than `rfc3339.mbt`'s own nested-match code, though the existing RFC 3339 code was left as-is rather than retroactively restructured to match, avoiding unnecessary risk to already-shipped, already-tested code.
- [x] Named convenience format-string constants (Go-style `RFC1123`/`Kitchen`/`Stamp*`/`DateOnly`/`TimeOnly`-equivalents), once the specifiers they depend on exist. Pure data — each is just a `String` constant built from already-existing specifiers, no new render/parse logic. Named in `snake_case` (`rfc1123`, `kitchen`, `stamp`, `stamp_milli`, `stamp_micro`, `stamp_nano`, `date_only`, `time_only`), matching `moonbitlang/core`'s own convention for public constants (e.g. `Int::max_value`) rather than Go's PascalCase — this project already translates Go/chrono concepts into its own idiom throughout (strftime-style specifiers instead of Go's reference-time layout, per the Architecture Decisions above), so the constants are built from `%`-specifiers, not copied as literal Go layout strings. `kitchen` (`"%-I:%M%p"`) depends on the padding-flag modifiers item just before this one (`%-I` for the unpadded 12-hour clock) — confirmed directly against Go's own source that `"3:04PM"` renders hour unpadded. `stamp`/`stamp_milli`/`stamp_micro`/`stamp_nano` depend on `%3f`/`%6f`/`%9f` from two items back. `rfc1123` (`%Z` unparseable), `kitchen` (no seconds), and the `stamp*` family (no year) don't carry enough fields to round-trip through the matching `parse_*` function on their own, matching Go's own documented intent for `Stamp` (display alongside separately-known context) — only `date_only`/`time_only` are self-sufficient for parsing. ## Phase 12: API Consistency Review Follow-ups

Reference: an audit of the generated `.mbti` interfaces of `core`, `tz` and `format` for self-contradictions and inconsistent design, run before the first release because a public rename or a changed failure mode is a breaking change afterwards. Items marked "verified" were confirmed against the implementation; the rest were read from the `.mbti` only. Per this project's standing practice, the approach for each item (and its coverage target) is confirmed with the user before implementation starts, and an item may be resolved by recording an Architecture Decision instead of changing code.

### Contradictions (verified)

- [x] `add_signed`/`sub_signed` failure mode differs by type: `NaiveDate::add_signed` returns `Self?` and has no `checked_*` counterpart, while `NaiveDateTime::add_signed` and `DateTime::add_signed` abort on overflow with `checked_add_signed` as the `Option` form (the convention `NaiveDate::add_days` also follows). Decide whether `NaiveDate` moves to the abort/`checked_*` pair (breaking) or the exception is recorded (resolved: `NaiveDate` moved to the abort/`checked_*` pair)
- [x] `DateTime[Tz]` `Eq`/`Hash` and `Compare` disagree: `Eq`/`Hash` are derived over `(datetime, tz)`, while `Compare` orders by the UTC instant alone (and requires `Tz : Eq` needlessly). Two values of the same instant in unequal zone values compare `0` but are not equal. Decide among: instant-only `Eq`/`Hash`, dropping `Compare` in favor of `compare_instant`, or documenting the contract (resolved: `Eq`/`Hash`/`Compare` all use the instant; recorded as an Architecture Decision. `Location` equality itself is still open in its own item)
- [x] `TimeDelta` arithmetic (`add`/`sub`/`mul`/`div`/`sum`) returns `Option` under the plain name, while every other type reserves the plain name for the abort form and `checked_*` for `Option`. Decide between unifying the convention and recording `TimeDelta` as a documented exception (resolved: unified on the abort/`checked_*` convention)
- [x] `DateTime::years_since(Self[Tz], Self[Tz])` requires both operands to share one `Tz`, while `signed_duration_since` and `compare_instant` accept `Tz2`; it also compares the local dates of each operand (`date_naive()`), so across two zones the two sides are read in different local calendars. Decide whether to accept `Tz2` (and state which calendar is used) or keep the single-`Tz` restriction and record why (resolved: accepts `Tz2`, and reads both dates in the receiver's time zone)
- [x] Failure reporting uses four mechanisms: `Option` (constructors, `checked_*`), abort (plain arithmetic), `Result[T, RoundingError]` (`round`/`round_up`/`truncate`, a plain `pub(all) enum`), and `raise ParseError` (`format`). `RoundingError` is returned as a value while `ParseError` is a `suberror`, so a caller handles the two with different syntax. Decide whether the rounding family should `raise` a suberror, or record the split by failure kind (resolved: recorded as an Architecture Decision; `Result[_, RoundingError]` is kept)
- [x] Argument order differs between the two `parse_*` families (verified in `parse.mbt`): `parse_items(items, input)` and `parse_items_and_remainder(items, input)` take the pattern first, while `parse_date(input, fmt)`, `parse_time`, `parse_date_time` and their variants take the input first; `format_*_items(value, items)` puts the value first. Decide on one order before release, since swapping two same-typed-looking positional parameters is a silent breaking change (resolved: subject first, pattern second everywhere; `parse_items`/`parse_items_and_remainder` now take `(input, items)`)
- [x] The sub-second rounding family disagrees on failure mode (verified in `naive_time.mbt` and `naive_date_time.mbt`): `NaiveTime::round_subsecs` is total and wraps past midnight, silently discarding the day carry, while `NaiveDateTime::round_subsecs` and `DateTime::round_subsecs` return `Result[_, RoundingError]` (`OutOfRange` at the top of the range). An out-of-range `digits` (outside `0..=9`) aborts in all three, whereas an invalid `TimeDelta` granularity is `Err(InvalidGranularity)`, so one kind of bad unit argument has two failure modes. `NaiveTime` also has no `round`/`truncate` taking a `TimeDelta`. Decide whether `NaiveTime::round_subsecs` should expose the carry (like `overflowing_add_signed`) or be documented as wrapping, and whether `digits` should be rejected the same way as a granularity (resolved: `NaiveTime::round_subsecs` documented as wrapping; `digits` stays an abort per the abort-contract item; no `TimeDelta` `round`/`truncate` added to `NaiveTime`, recorded as an Architecture Decision)
- [x] `TzifData::transitions`/`transition_types`/`local_time_types`/`leap_seconds` return the internal `Array` without copying (verified in `tzif.mbt`), so a caller can mutate a value whose `Eq`/`Hash` are derived over those arrays, contradicting the immutable-first design (`NaiveWeek::days` and `WeekdaySet::to_array` build fresh arrays). Decide between returning copies, returning `ArrayView`/`Iter`, or documenting the aliasing (resolved: the accessors return copies; `Location` reads the private fields directly)

Other resolution policies (later instant of a fold, snapping to the gap's edge) have no spelling, and `from_ymd_hms` has no lenient counterpart, so a caller with components must go through `NaiveDateTime::new` first. Decide whether the name and the single fixed policy are final, and how it relates to the two-spellings item above
- [ ] `Utc::now()` is total and unwraps internally (verified in `now.mbt`: `from_timestamp_millis(...).unwrap()`), so a host clock outside the representable range aborts, while `Local::now()` returns `DateTime[Local]?` for its own failure. Decide whether `Utc::now` should share the `Option` form or the clock is documented as always in range, and state in both docstrings that they read the host clock (the one nondeterministic read in the library)
- [ ] `single` names three different roles: `WeekdaySet::single(Weekday)` constructs a set, `WeekdaySet::single_day()` reads the lone member back, and `MappedLocalTime::single()` extracts the value of the `Single` case. The constructor/accessor pair on `WeekdaySet` is not spelled symmetrically (`single`/`single_day`) and the third use is unrelated. Decide whether to rename one side (for example `WeekdaySet::of`/`only`) before the names are frozen
- [ ] `DateTime::round`/`round_up`/`truncate` operate on the UTC instant, not the local reading (verified in `date_time.mbt`: they delegate to `self.datetime`, and the docstring says an hour granularity may still leave a non-zero local minute). In a zone with a non-whole-hour offset (for example `+05:30`) `truncate(1 hour)` therefore returns a local time that is not on the hour, and the methods need no `TimeZone` bound while `DateTime::round_subsecs` and the calendar accessors read the local side. Decide whether rounding should act on the local reading (which can land in a gap or fold and so would return `MappedLocalTime`), stay on the instant with the rule stated on every rounding method, or be withdrawn from `DateTime`
- [x] `DateTime::from_ymd_hms` returns `Absent` for an invalid component (for example month 13) as well as for a local reading inside a DST gap (verified in `date_time.mbt`), the same conflation as the `with_*` item above, but on a constructor where `NaiveDate::from_ymd` and `NaiveTime::from_hms` report invalid components as `None`. `format::parse_date_time_in` returns `MappedLocalTime` too. Decide whether invalid components should be separated from `Absent` for every `MappedLocalTime`-returning entry point, or the merge recorded once as a decision (resolved: the merge is recorded as an Architecture Decision and stated on `MappedLocalTime`)
- [ ] `NaiveDateTime::new(date, time)` and `NaiveDate::and_time(time)` are two spellings of the same total combination, alongside `NaiveDate::and_hms*` (`Option`); the zoned side has `DateTime::from_local` only. Decide which is canonical (this sits beside the `from_utc`/`from_utc_datetime` item above)
- [ ] `succ`/`pred` mean different things by type: `Month::succ`/`pred` and `Weekday::succ`/`pred` wrap around, while `NaiveDate::succ`/`pred` abort at the range limit (with `succ_opt`/`pred_opt` as the `Option` form). Decide whether the shared name is acceptable and state the wrap or abort rule in each docstring
- [ ] `NaiveTime` spells time arithmetic `wrapping_add_signed`/`wrapping_sub_signed` and `overflowing_add_signed`/`overflowing_sub_signed`, with no `add_signed`/`checked_add_signed` pair, while `NaiveDateTime` and `DateTime` use `add_signed`/`checked_add_signed`. The wrapping behavior is intrinsic to a time of day, but the vocabulary is a third one beside the abort and `checked_*` convention; decide whether `NaiveTime` keeps its own vocabulary as a documented exception
- [ ] `DateTime::add_days`/`add_months`/`add_years` (and their `sub_*` and `checked_*` forms) shift the stored UTC date, not the local one (verified in `date_time.mbt`; decided earlier and recorded only in the `DateTime` checked-arithmetic item), while the accessors, `with_*`, `years_since` and `from_ymd_hms` read the local calendar, and the docstrings say "keeping the time of day" without naming the reading. In a zone away from UTC the two calendars differ: at `+09:00`, local `2024-01-31 08:00` plus one month is `2024-03-01 08:00` (the UTC date `2024-01-30` clamps to `2024-02-29`, which reads as `03-01` locally), whereas the local calendar gives `2024-02-29 08:00`; across a DST change the local time of day also shifts. The methods need no `TimeZone` bound, unlike the local-reading ones. Decide whether calendar steps should act on the local reading (which can land in a gap or fold and so would return `MappedLocalTime`, as `with_*` does), stay on the UTC date with the rule stated in every docstring and README, or be limited to `add_signed`; this feeds the `DateTime::round` item below
